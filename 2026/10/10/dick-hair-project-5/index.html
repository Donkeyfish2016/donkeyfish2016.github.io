OMG，“日记”进度已经落后十天了，孩子们这并不好笑🥲。经过我的一番思考，我觉得果然还是先记录（学习）后端部分的东西吧，至少先把这部分跟进了再说，不然的话，前端本身懂得就不多，还是等之后种草期整顿的时候再仔细研究吧。

10月1日

说回这部分，那天主要是初步实现了热榜统计的功能。热榜嘛，就是那个按曲目播放量排名，然后会实时“咕噜咕噜”滚动的的那个（那算啥^^;）。

一、 从技术选型说起

1. 为嘛传统的 CRUD 不行？

简单思考，这不就是 SQL 的 分组聚合COUNT + ORDER BY + 分页 语句吗？因为在第三话中，我们已经进行了播放事件埋点，这意味着我们有播放事件的数据记录。那直接查 PLAY 类型的事件，然后按曲目 ID 分组，统计播放量，最后按播放量排序，再分页，介不就完了么？如果只是要数据，那这么做确实可行，而且很好，因为不麻烦。但是作为实时热榜，就像上面说的，它会“咕噜咕噜”滚，如果我们只是查数据然后暴露 REST 接口的话…首先它不会自己刷新，所以看的人要手动 F5 才能获取最新数据；其次每次都要查数据库，那么多播放事件条目在，那不炸了。所以为了解决这些问题，我们需要考虑其他的路子。

2. 解决方案规划

既然不可能每次都去数据库重新统计，那么自然会想到使用我们已有的缓存中间件 Redis 来存储热榜数据，于是问题就变成了：存什么？用什么存？怎么存？

存什么？自然是每首曲目的播放次数咯；那么用什么存呢？先想想热榜对于数据有什么要求：首先，一首歌对应一条数据，不能重；其次，虽然读出来排序也可以，但若是能在内存的有序集合中排好那自然再欢迎不过了。同时满足这俩条件的，果然就是 ZSet 了吧：自带 score 排序，不怕重复，甚至还有 ZINCRBY 累加和 ZREVRANGE 取 Top N。

既然选择了 Zset 数据结构，怎么存呢？最朴素的想法当然是维护一个 ZSet，然后把所有播放都 ZINCRBY 进去，但问题在于，这是个实时热榜哦，总不能让老资历永远挂在顶上罢。哼嗯，或许我们会想到，既然实时，那每小时清一次不就行啦🤓，但这样的话刚清完那会儿热榜会变得空空如也…于是，我们有分钟桶 + 滑动窗口的策略：为每分钟维护一个 Zset，其中存放 trackId -> playCount，查询时使用 ZUNIONSTORE 聚合最近60分钟的曲目播放次数，然后 ZREVRANGE 取前几名即可。

存储数据的问题解决了，接下来的问题就是如何让它自己刷新了。比较直观的方法，既然我们可以暴露 REST 接口，那由前端定期发起请求不就行了（短轮询策略）？但是这样前端需要持续发起请求。那我们就尽量减少请求次数，使用长连接请求数据，直到有新数据可用或超时呗（长轮询策略）？这样…服务器还是要维护好多好多的挂起连接哇。或许我们会想到 WebSocket ，但它是全双工的，我们的场景只需要后端单向发消息给前端…于是，会考虑使用 SSE 来应对这个场景（这家伙最近火爆了哇，说到AI流式对话就是 SSE ^^;），其单向通信的性质完美匹配该场景，甚至它内置实现了自动重连（保活），Spring MVC 中也有 SseEmitter 支持，浏览器也大多有原生支持…中👍

虽然 SSE 很中，但有个小问题果然还是要指出来，浏览器原生 EventSource 没法鉴权，因为它不走我们的 axios 拦截器。若是需要鉴权的话，前端就会稍微麻烦一点。但这里无所谓，直接放白名单😈。且听说在部署阶段，这块可能也会有些坑，但那些到时候再说吧，车到山前必有路，人到坟前自然死😌。

于是通过以上的策略讨论，应用这些技术，我们就终于（理论上）得到了一个分钟级的实时热榜，每分钟都会“咕噜咕噜”的那种！

二、 Redis ZSet 热榜数据存储

理论可行，实践开始😋。

1. redis key 设计简述 与 埋点

先简单说一嘴 key 设计，既然是按分钟分桶，那么时间戳就具有天然唯一性，所以我们的 key 可以很顺溜地设计成 xxx:{yyyyMMddHHmm}。对于 Zset 数据结构，value 就是 xxx:trackId，score 就是其当前分钟播放次数。然后捏，这些数据肯定不能无期限地存在 redis 里，毕竟那可是宝贵的内存，不像 Constant.java 一样可以当字段垃圾桶用（Constant.java：你礼貌吗），所以我们需要给它一个合适的 TTL，这里我设为 90 分钟（60 分钟窗口 + 30 分钟余量）。

然后是埋点。前面我们提到的 ZINCRBY 自然是应当在曲目播放时调用的，所以最简单的策略就是直接跑到 TrackController 里，给票据那个接口加一句调用，但这么写太吊毛了显然不行。在第二话中，我们已经在一次性票据生成接口中埋了播放事件生产者，所以这边也直接走消息队列异步处理就是了。于是，我们的做法就是在播放事件消费者中加一句：它现在不止处理 MySQL 落库，还要处理这部分的 ZINCRBY。
