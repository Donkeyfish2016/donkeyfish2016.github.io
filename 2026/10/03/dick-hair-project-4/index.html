吊毛项目日记(四) - 分片文件上传

Created2026-10-03|Updated2026-10-08
|Post Views:

OMG，说起来有个很搞笑的事，这部分我跟着AI爷迷迷糊糊地混完之后，才开始思考：Minio SDK 底层明明实现了自动分片功能（那套 S3 Multipart Upload 机制），为啥我还要自己手写一套？真是因果倒置我测^^;)

9月29日 ~ 9月30日

果然还是先从这个文件上传模块究竟是在做什么开始罢。

一、 WHAT AM I FUCKING DOING?

文件上传？后端实现个上传接口，然后前端用 Element-plus 提供的现成组件联调一下不应该就完事了嘛？Minio 第二话都配置好了耶。确实，这样很好，甚至对于大文件，Minio SDK 调用的 Minio 服务端也提供了自动分片的功能…但是，还有些问题是仅仅这样所满足不了的😢。

1. 数据存储端可拓展性

最开始在跟着黑马做那个智能学习辅助系统的时候，我就没搞 阿里云OSS，而是在自己机子上搞了个 Minio 服务端。所以现在这个项目也是理所应当的用了 Minio 作为曲目存储的数据库。但是，万一哪天我脑疾发作，突然想搞事换到 阿里云OSS 呢？那不完犊子了，整个这个模块都要重新写。就像软工导作业，要求用Json文件存数据，万一哪天发癫又叫你用数据库呢？这不，面向接口编程，存储抽象层。

2. 浏览器直传

从数据流的角度来说，MinIO 服务端完全支持客户端（如浏览器）通过预签名 URL 直接上传分片，而不经过我的 Java 后端。但是 SDK 并没有提供可以直接拿来主义的方案，且对于分片，SDK 会自动在服务端进行分片。这显然会增加后端的压力（哦谢，但说到底能增加多少^^;），所以为了让 Java 服务零带宽消耗，我们需要整理好预签名，直接返回给前端，然后前端直接去打 Minio。等待前端直接传完，再呼叫 Minio 进行合并。

3. 断点续传 与 会话信息管理

MinIO 服务端能够“记住”已上传的分片，但 MinIO 自身不会主动“恢复”上传。它只是被动地保存了状态。因此，我们需要利用这套分片状态的“记忆”，来自己实现断点续传的功能。而且，它也不知道在我们的服务中：本次上传是由谁发起的、当前处于生命周期的哪个阶段、传完之后干嘛…所以，Java 后端实际上是运用 Minio 服务端那一套对 S3 Multipart Upload 机制的实现，来编排整个文件上传的流程，以达到我们的目的。

(嘛，虽然有的地方对的不是很齐，但可读性还是有的…吧)

三、 上传会话管理

正如前面所言，我们需要保存每次上传会话的信息，包括但不限于：文件本身的元信息，本次上传分片的数目和大小，关联的用户/曲目 ID ，会话状态（已上传、上传中…）等。那么把它保存在哪里呢？作为会话信息，我们可以选择将它保存在内存中，也可以选择将它保存在数据库中。但我感觉这里落表有点多此一举，所以这里选择了 Redis。因为它可以设置 TTL，且它的 Hash 结构很适合存储这种信息。

DTO 实体类的设计取决于需求，本项目中包含上面的那些字段。对于会话状态，也没用枚举类，直接用一个字符串型，然后往常量垃圾桶里丢了几个字符串^^;)

然后对于服务类，所需要的基本也就是增（创建上传会话并存入 Redis）、删（完成或中断后删除会话）、改（一般是更新会话状态）、查（根据会话 ID 查询会话信息、判断会话信息是否过期或失效）。实现时注意把所有字段值都转成 String 再存进去哦。

关于这些千奇百怪的 DTO，它们都只是把前端/当前请求需要的值进行了封装，搞这么多而不是把所有字段都塞到一个实体里，只是为了自己看着清晰一点。

接下来，我们来看看这些服务接口都需要做些什么，它们如何组织前面所做的一切呢？

对于 initUpload ，它要做的可以分为以下几步：

  1. MD5 秒传检查：查询 audio_asset 表是否有相同 MD5 的已就绪曲目，若有则跳过上传，直接返回数据库结果（所谓秒传）；
  2. 确定分片大小和总分片数；
  3. 调用存储抽象层的 initMultipartUpload 初始化上传会话，获取 uploadId；
  4. 调用上传会话服务类的 createSession 创建 Redis 上传会话，保存会话信息；
  5. 调用存储抽象层的 generatePresignedUploadUrl，为所有分片生成预签名 URL；
  6. 返回数据给前端（若拿到 URL，就可以不过 Java 直传 Minio 了）。

对于 completeUpload ，它要做的可以分为以下几步：

  1. 调用上传会话服务类的 getSession 查询会话信息，判断会话是否合法；
  2. 调用存储抽象层的 completeMultipartUpload 合并所有分片；
  3. 调用上传会话服务类的 updateSession 更新会话状态；
  4. 返回合并后的 objectKey。

对于 abortUpload ，它要做的可以分为以下几步：

  1. 调用上传会话服务类的 getSession 查询会话信息，判断会话是否合法；
  2. 调用存储抽象层的 abortMultipartUpload 取消上传会话；
  3. 调用上传会话服务类的 updateSession 更新会话状态。

对于 getPresignedUrl ，它要做的可以分为以下几步：

  1. 调用上传会话服务类的 getSession 查询会话信息，判断会话是否合法；
  2. 调用存储抽象层的 generatePresignedUploadUrl，为指定分片生成预签名 URL；
  3. 返回所需数据给前端。

对于 getUploadStatus ，它要做的可以分为以下几步：

  1. 调用上传会话服务类的 getSession 查询会话信息，判断会话是否合法；
  2. 调用存储抽象层的 listUploadedParts ，获取已上传分片列表；
  3. 计算/返回相关数据给前端。

有了整体思路，接下来就是编码实现啦（都是AI爷干的我还真是大言不惭^^;），嘛，总之，至此，服务层的编排就暂时告一段落了。至于文件上传控制层？那就是把这几个全部包一层变成 REST API 就行了。
