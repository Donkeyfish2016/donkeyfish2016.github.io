流式播放数据返回接口的基本实现

既然爬了数据，作为一个电台项目，下一步自然就是播放音乐了。

一、 集成Minio客户端

这也是老同志了，只是新版本似乎带来了不少变化，当然写流式接口的时候我还没发觉😔

1. 引依赖，Springboot4得用新版依赖了

这行注释里带来的变化还是消耗了我不少时间呐…

2. application.yml 配置 和 配置类

字段值都是映射到配置类里的，说到这个，我还是习惯性地把Properties和Config的内容写到一起了，然后给一个类同时挂上 @Configuration、 @ConfigurationProperties(prefix = "minio") 俩注解。另外对于配置类，都直接加上 @Data 比较好喔，Spring 配置项值写入是靠 setter 的。

关于配置类，把字段写进去，然后注册个客户端的Bean就行了，没啥特别的。

3. 音轨实体设计

实体方面，主要考虑的就是各dto/vo哪些字段该带哪些不该带，但这些AI基本能考虑的很全面。接下来需要注意的就是，当时设计表的时候，曲目metadata字段的类型是JSON，但在实体类映射为String，然后用hutool手动解析。后续或许可以考虑直接用json类型接收？

另一个需要注意的就是这个 TrackStreamContext DTO。它真的很认真的执行了数据传输对象的职责。由于Controller 不能拿着一个 Track 实体就去播放，所以需要这个 DTO 来承载/传输播放所需要的数据字段。哦对了，当前 contentType 是写死的哈哈😓

4. 三层架构-服务层

与一般CRUD服务层不同的地方在于，它需要提供一个准备流式播放信息的接口，但本质还是查询操作，只是这个查询结果不会直接返给前端了。

然后就记录下MybatisPlus分页查询相关的内容吧。这倒是与使用Mybatis + PageHelper很不一样，也没有“只有紧挨着的下一句才能分”之类的限制。

首先还是需要一个查询条件呢。然后构造eq、like、between、orderby等查询条件。完了之后执行分页查询（就是加limit子句）返一个 IPage<TrackVO>。这里直接把 Page<TrackVO> 做参数传进去了，实际上只是想要当前页和每页数量。

另外，MyBatis-Plus 分页需要配置分页插件。否则 selectPage 不会自动加 LIMIT，会把全表数据查回来。写个配置类注册个MybatisPlus拦截器的Bean。

5. 三层架构-控制层

说到这个播放控制层，首当其冲的就是 302 和 206 两种播放音乐的方式了。

先说 302，”服务器返回一个临时重定向地址。浏览器的 <audio> 标签收到 302 后，会自动用新预签名 URL 重新发起请求。在本项目中也就是直接往 MinIO 请求文件”。

控制层方法只需要根据目标曲目相关信息返回预签名url即可。

重头戏果然还是在 206。”客户端发请求时带 Range: bytes=0-1048575 头，服务器只返回请求的那一段字节，响应头包含 Content-Range: bytes 0-1048575/5000000（已传范围/总大小）。这是 <audio> 标签拖动进度条时浏览器的标准行为”。

对于 206，控制层需要负责实现以下几件事：

  1. 查库拿元信息。
  2. 处理 HTTP Range 头。这需要覆盖三种情况：
    • “bytes=-512” → 最后 N 字节
    • “bytes=1024-“ → 从 N 到末尾
    • “bytes=0-1023” → 精确区间
  3. 构造响应头。包含 Accept-Ranges、Content-Range、状态码 等。
  4. 返回流（InputStreamResource OR StreamingResponseBody？）。

前三步的编码直接交给AI爷，主要是第四步返回时，出现了点小问题，在说起这个问题之前，就不得不提一下从Minio按起点和偏移拉数据的逻辑：

嘶，我们拉取到一个 InputStream，然后在 Spring Framework 的 ResponseEntity 当中将其包装为 InputStreamResource，那么问题来了，谁负责关闭这个输入流🤔？

Consider retrieving the InputStream on demand if possible, reducing its lifetime and reliably opening it and closing it through regular InputStreamSource.getInputStream() usage. 来自 SpringFramework相关文档。这意味着 InputStreamResource 不会自己关闭输入流…

或许，很容易想到 try-with-resource 嘛，但是这样真的可以吗？

方法返回后，try-with-resource 反手把这个流给关了，那 Spring MVC 还怎么读咧？

此路不通，再想想别的办法。自己再把 InputStream 包一层让它结束时自己关？听起来很麻烦，还有增加不必要的类；写一个过滤器，在ThreadLocal里记录所有打开的输入流，结束时统一关闭？这要加的也太多了…好在我们有 InputStreamResource。

至于这个东西具体怎么玄妙，俺也不懂。但俺知道的是，控制层返回 StreamingResponseBody 时，Spring MVC 自动切换到异步处理模式，欸，在另个线程写响应，写完才返回，也就是说 writeTo 是个完整的方法调用，那这不就意味着…我们可以在这个方法里 try-with-resources ，确保流在方法结束时关闭！

爽了，这下它终于闭上了。

1. STORE-Pinia登陆状态管理

先说说这个呆萌的🍍是啥。

Pinia 是 Vue 的官方状态管理库，多个组件/页面需要共享同一份数据时，直接把数据存到这里面就行。需要注意的是 Pinia 不是数据库，我理解 createPinia() 创建后，它就是一个 JS实例 ，实例内部用 Map 保存所有 store，故而所有内容都存储在 JS 运行时堆内存里。所以刷新页面后，如果没有持久化，里面的东西就没了。毕竟 F5 是浏览器级别的重新加载。但路由不会，因为它是vue应用内部的操作，所以可以放心用它在不同视图间共享数据。

所以，Pinia 本身不负责持久化，这个额外需求需要自己实现。说到浏览器存储，那就是 localStorage、sessionStorage、cookie 这些，当然整个数据库存也是可以的。本项目选择的是 localStorage，因为基本就是个登录场景。

接下来是我学习过程中认为很重要的几个概念：

一个 store 主要包含：

  • state：共享的数据，类似组件里的 data / ref
  • getters：基于 state 计算出来的值，类似 computed
  • actions：修改 state 的方法(function)，可以同步也可以异步

而定义 Pinia store，并指定其中内容的方法，可参考其示例文件 counter.js，其中使用的定义方法叫做 Setup Store，我了解到还有另外一种定义方法叫做 Options Store，显式分区这三者。但既然示例文件都是 Setup Store，我也就不增加自己的记忆负担了嘻嘻(●’◡’●)

2. <audio>标签

这里的 streamUrl 最终返回的是 /api/track/${id}/presign ，没错，最开始使用的是重定向的方式。因为在后端中，这个请求已经被加入了白名单（它不能带两种认证方式嘛）。这对于无法自动携带 Authorization 头的 <audio> 标签是很合适的。毕竟，<audio> 标签发起的 HTTP 请求是浏览器原生行为，不会经过 Axios 拦截器。

四、 登录的流式播放-一次性票据

说到登录鉴权，我们看重的就是那个携带了用户信息的 token。那么类似的思路，能否让每次播放都携带一个具有验证性质的一次性“票据”，有票才给播，不然不给放？然后我们就可以放心大胆地把 stream 流式播放请求加入白名单，而把 ticket 票据接口拦下。没登录意味着拿不到票，自然也就没法播放了。
