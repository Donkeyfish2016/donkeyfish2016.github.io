二、 ThreadLocal上下文和全局异常处理器的初步实现

这两个东西应当是在拦截器之前写好的，记录下实现过程。

1. ThreadLocal上下文的实现

ThreadLocal 是JDK 原生工具，和 Spring 无关。

这个东西不跨线程，每个线程都有自己的副本，互不干扰。需要注意的是内存泄漏问题，Tomcat 使用线程池，线程不会销毁，会放回池子复用，所以在拦截器检查完后需要进行清除。

从实现角度来说，这个好像没啥要注意的，基本这种项目都是存个用户id^^;)

2. 全局异常处理器的极简实现

@RestControllerAdvice 是 Springboot 提供的注解。

这个的极简实现也没啥特别要注意的，随着自定义异常的增多，这个处理器也会变复杂。

三、 单层token登录校验的实现

接下来是拦截器的编写，主要涉及三个类：JwtUtil 、 JwtLoginInterceptor 、 WebMvcConfig，其中对于 JwtUtil ，其实说不定可以拆个 JwtProperties 出来，用来配置 JWT 相关的参数，但因为是后面才想到的，也就没有太史慈了^^;)

1. 依赖与配置

jjwt 0.11 及更早的旧版本，整个包都打在一起。0.12 之后官方拆成了三层。这也就是为什么黑马的talis智能学习辅助系统里只引了一个依赖，但这里要引三个。

然后是关于配置项，这个在老项目中是写死在 JwtUtil 类里的，现在为了看着高级(没事找事)一些，把它放到 application.yml 里。其实如果可能，请求头相关(像 tokenName: Authorization 、tokenPrefix: Bearer )啥的也可以放到这里头，所以说可以单独拆个properties类出来，但终究是错付了。

然后还有个小问题，是关于 @Value("${jwt.secret}") 字段注解，和 @ConfigurationProperties(prefix = "jwt") 注解的。需要注意的是后者需要依赖于setter使用，所以在这里使用前者。对于properties类这种一般会加上 @Data 注解的，后者会比较方便我感觉。

2. JwtUtil的实现与功能

JWT 不是加密，是签名。payload 里的内容 base64 就能解码看到，所以不要往里面存密码等敏感信息，只存 userId 就够了。签名的作用是「保证内容没被改过」。

这个实现没啥说的，就是个工具类，用来生成/解析 JWT。而且新版本的jjwt在这部分的api有一定改动，说不定过段时间又会有改动，随查随写便是。然后由于没有properties类，手动给它加上几个getter会比较好。

另外还有个比较有趣的点就是，对于这种工具类，往往会面临静态方法或注册为Bean的问题。这里尝试了跟老项目不同的方式，注册为Bean，然后在需要的地方注入。

二、 双token拦截机制的实现

简单说下我对这个机制的理解：

双token拦截机制是一种权衡安全与用户体验的登录机制，它在用户登录后，生成两个token： access token 和 refresh token。
access token 用于每次请求，它泄露了就可能有人来乱搞，但是单token模式下其无法主动失效，只能等待过期（一般都是两周吧差不多）。
于是引入 refresh token 用于刷新 access token，这样可以缩短后者的过期时间，而让前者保持较长的过期时间，减少了别人用后者乱搞的风险。

1. JwtUtil，拦截器，WebMvcConfig的改动

对于JwtUtil，新增了生成refresh token的方法，同时新增字段 refreshExpiration ：

对于拦截器，编写了第二层拦截器，只拦截 /refresh 请求。有两个我认为需要注意或有待改进的点：

其一，与第一层access拦截器的核心差异在于其需要去redis进行校验。

其二，我直接把refresh token存储在请求头中，且请求头是硬编码的。

对于后者倒好说，只是不够优雅的问题。但对于前者，我了解到有一种方式不需要前端在手动在 header 塞 G‑Refresh‑Token ：将 refresh token 储存在 HttpOnly Cookie 中，并用自动 Cookie 发送。但这种方式虽然是生产上的最佳实践（豆姐说的😓），但实现起来很复杂的亚子，我也不太懂，这里现留下。

对于WebMvcConfig，注册两层拦截器。注意access层排除 /refresh 请求，refresh层仅拦截 /refresh 请求。还要注意注册的先后顺序。

2. 三层架构方法的改动

登录方法login的改动：新增了生成双token，和把refresh token存储到redis中的逻辑。

刷新方法refresh的编写：主要完成新access token的生成。

需要考虑的有两点：

其一，关于refresh token过期时间的刷新。这个我还拿不定主意是否要保留。保留，好处是不会出现用户还在使用应用，就突然要重新登陆的情况；但坏处就在于它要访问redis了，丧失了无状态性能优势。

其二，关于jwt加密对象的选取和最终user是否需要返回。为了避免在refresh方法中增加访问数据库的逻辑，我决定access token只加密userId，而refresh token保留一开始的claims加密。并且返回相应vo时，用户信息留null。

对于此修改，要记得同步去进行拦截器的修改，不然取不到正确的东西（jwt中subject()和claims()取法不一样），别问我怎么知道的😔

剩下logout方法（删除redis中的refresh token），以及Controller层的改动没啥可说的，正常写就是。
